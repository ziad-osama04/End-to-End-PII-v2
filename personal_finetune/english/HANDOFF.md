# English-track handoff: the full story from Dutch through French, and how to build English

This document is written so you can hand it directly to a fresh Claude Code
session (paste the whole thing as your first message) with no other context
needed. It covers, in order: (1) what shipped for Dutch and every error
found building it, (2) the complete chronology of building French —
every bug, every validation pass, every new document genre, in the order
they actually happened — and (3) the exact open decisions and method for
English. Part 2 is long on purpose: almost every bug found while building
French was a *class* of bug, not a one-off, and the same class is very
likely to reappear in English if this history isn't read first.

## 0. Project context (read this first)

This repo (`End-to-End-PII-v2`) has an ongoing PII-detection fine-tuning
track under `personal_finetune/` (+ `TamerBERT/TamerBERT/`). It fine-tunes a
RoBERTa-family model per language to detect PII (names, dates, addresses,
national ID numbers, phone numbers, etc.) in synthetic medical documents,
using entirely synthetic training data generated by a Python script — no
real patient data is ever used.

**The project is expanding to 5 more languages**: French, English, Romanian,
Spanish, German. Architecture decision already settled (don't re-litigate
this): **per-language monolingual models**, not a shared multilingual model
and not zero-shot. A published study (arXiv:2412.10918) trained separate
expert models for exactly these 5 languages and got F1 0.95-0.98 across all
of them, beating GPT-4o; general/zero-shot multilingual PII models cap out
around F1 0.6 regardless of architecture family. Only real in-domain
fine-tuning gets to 0.95+. Routing/language-ID has its own real risk
(degrades on short/noisy/code-switched text, fails silently) — not a
shortcut worth taking.

**Critical fact about this whole project, easy to miss**: French and
English tracks are both **Belgian**, not France-French or UK/US-English.
Belgian-national identifier formats (INSZ national-registry number with its
real mod-97 checksum, RIZIV healthcare-provider number, IBAN "BE" prefix,
Belgian phone area codes) are **shared across every language track** — they
don't change with the document language, only the surrounding prose and the
LABEL WORD used for each identifier does (see section 3.3b — this exact
point caused a real, widespread bug in French).

**Status of each track as of 2026-08-18**:
- **Dutch**: shipped, done, not being revisited. `farahelmashad/pii-medroberta-nl-v2`, indist F1 0.988, OOD F1 0.803, built on `CLTL/MedRoBERTa.nl`.
- **French**: base model chosen (`almanach/camembert-bio-base`). **Data-generation phase is complete and fully validated** — 56 templates across 12 document genres, full validation suite passing at 0 errors. This is your reference implementation for *method*, not content. Kaggle training/eval/quantization has NOT started yet for French — that's the next phase, out of scope for this handoff.
- **Spanish**: base model chosen (`PlanTL-GOB-ES/bsc-bio-ehr-es`), data generation not started.
- **English, Romanian, German**: nothing started yet, including base model selection.

Infra rules that apply to every language track equally (already learned the
hard way once, don't relearn them):
- **Kaggle downloads**: always pass `--file-pattern` to `kaggle kernels output` — it's a *regex*, not a glob (`"*.log"` fails; use `.*\.log"`). Omitting it once began pulling ~500MB of model weights to the laptop.
- **The D: drive has a real, recurring hardware fault** (confirmed via Windows Event Viewer, not a software bug). If you hit `OSError: [Errno 22]` or "a device which does not exist was specified" on D:, don't debug it as code — route around it via system Python and a temp directory off D:.
- **Personal MLflow/HF Hub/model checkpoints never touch the local laptop disk** — push directly from the Kaggle kernel session via a companion "push" kernel using `kernel_sources` mounting (mount path is `/kaggle/input/notebooks/<owner>/<kernel-slug>/`, not the naive path). This whole track stays under `personal_finetune/`, separate from the team's shared `backend/src/detection/` code.
- `git push` is blocked by the permission classifier here — hand the command to the user rather than retrying it yourself.

## PART 1 — Dutch: what shipped, and every error found building it

Read this even though Dutch itself isn't being touched — every one of these
was a real, confirmed bug or a real, confirmed dead-end, and several
recurred (in a new form) while building French. Don't re-litigate any of
these; they're settled by rigorous testing.

**Settled architecture decisions:**
- Single **merged ADDRESS** label, NOT split into STREET/ZIPCODE/CITY — an explicit ablation showed splitting hurts real-document precision (1.000→0.968) with no compensating OOD gain.
- **`merge_drop_all`** merge strategy (regex excluded entirely for AGE/DATE/PHONE, the model owns them outright) beats `fallback` on every eval surface.
- Final label taxonomy: **model-trained** ADDRESS, AGE, DATE, NAME, ORGANIZATION, PHONE; **regex/checksum-only** INSZ, RIZIV, BTW_EENHEID, EMAIL, URL; **GENDER** is derived downstream from INSZ parity and is never a detected span.
- **Institutional/hospital names ARE correctly labeled NAME** (`ORGANIZATION → NAME` in the label scheme) — an earlier session originally flagged this as a bug ("institutional-name ambiguity") and almost built a fix for it. That diagnosis was **wrong**: confirmed by checking all 5 real ground-truth documents, where the hospital name is genuinely labeled NAME throughout. The one document that looked inconsistent had bad gold labels, not the model. Lesson: verify against ground truth before "fixing" what looks like model confusion.

**Bugs found and fixed, in the order they were found:**
1. **19-of-~69 templates had a literal-placeholder-leak bug** — literal text like `"DD-MM-YYYY"` or `"MM/YYYY"` baked into the template prose instead of a real `{DATE_...}` placeholder. Caught by a regex filter (`LEAK_RE = r"DD-MM-YYYY|MM/YYYY"`) now baked permanently into `prep_tamerbert_data.py` / `prep_data_fr.py`. **Apply the same filter (translated to whatever literal format-hint strings could appear) to English.**
2. **Three regex/checksum-layer bugs**, confirmed via real-document testing, not yet ported back to the original `patterns.py` source (check before assuming they're fixed upstream): (a) AGE false-positive on "above/below N years" reference-range disclaimer text; (b) a missing `YYYY/MM/DD` slash-separated date format; (c) INSZ/RIZIV regex failing whenever a sentence-final period immediately followed the number — fixed by narrowing the trailing lookahead from `(?![\d.\-/])` to `(?!\d)`. This third one had real, measurable impact on real documents (regex-only F1 on real docs rose to 0.988 after the fix).
3. **Casing lock-in**: ALL-CAPS documents collapsed the trained model to F1=0.613, Title-Case-Every-Word to F1=0.778 (vs ~0.98 baseline) — confirmed as a genuine *model* weakness, not a regex weakness (regex-only F1 stayed ~0.90-0.93 under the same transforms, since digit patterns are case-insensitive by construction). Fixed by adding a casing-transform augmentation round; measurably closed the gap on a genuinely fresh third-round OOD battery (never used to design the fix).
4. **Sliding-window boundary crossing was tested and confirmed NOT a real problem** — a span deliberately engineered to straddle a tokenizer stride-window boundary was still fully recovered via `resolve_overlaps`. Don't spend time re-testing this basic mechanism; do re-test it if you change the tokenizer/stride/architecture for a new language.
5. **The root cause of the OOD ceiling was narrow STRUCTURAL template diversity, not field-format diversity.** Format diversity per field (phone formats, date formats, name variety) was already excellent even in the first version. What was missing was structural/genre diversity — the whole training set was ~40-50 near-identical clinical-LETTER-shaped templates. This is the single biggest lesson carried forward into French, and the reason the French track ended up building 6 non-letter genres (lab report, pharmacy, radiology, sick note, prescription, discharge-meds) rather than just more letters — **do the same for English from the start, don't discover this gap the slow way a third time.**
6. Final OOD trajectory after fixing the above: strict F1 0.66 → 0.72–0.87 (round 1 fixes) → **0.803 shipped** (final, after two more rounds). OOD is a documented, accepted weak point of the shipped model, not something still being chased.
7. **Known, still-open debt**: two non-identical regex/pattern layers exist on the Dutch side (`backend/src/detection/dutch_regex.py` vs. the Kaggle track's own inlined regex in `train_and_eval.py`) and have never been reconciled. Don't assume a fix made in one is present in the other. Flag this for whoever owns the shared `backend/src/detection/` code, not something to silently fix yourself inside `personal_finetune/`.

## PART 2 — Building French: the complete chronology

This is the part to read most carefully — it's the actual step-by-step
history "from the errors we found until we reached the final dataset,"
across two build phases: the initial build, and a later "polish and
stress-test" pass that found real bugs the initial build had missed.

### 2.1 Foundational decisions (settled before any code was written)

- **Confirmed Belgian French (Walloon), not France-French** — this had to be explicitly asked and confirmed before any content was written, exactly like the open question flagged for English in Part 3. Once confirmed, all Belgian-structural code (INSZ, RIZIV, IBAN, phone) carried over from Dutch **unchanged** — only language-bound content forked.
- **Base model: `almanach/camembert-bio-base`** (CamemBERT-bio), chosen via a research brief comparing 8 candidates on architecture fit, license, and independently-published clinical-NER benchmarks (won or tied-best on every French clinical corpus tested: DEFT, E3C, QUAERO/MEDLINE, QUAERO/EMEA). Same RoBERTa family as MedRoBERTa.nl, so the existing tokenizer/sliding-window/BIO-decode pipeline drops in unchanged. **Do the equivalent research brief for English before picking a base model** — don't skip straight to `roberta-base` or a generic BioClinicalBERT without comparing real candidates and their license terms.

### 2.2 Recovering the real templates — three attempts, two of them buggy

The ~50-69 original Dutch templates that built the shipped model no longer
exist as source files — only `TamerBERT/TamerBERT/train.jsonl` (6,417
rendered documents, 69 unique `template_hash` values, ~93 docs each)
survives. Recovering the masked templates from it went through **three
iterations** — read this closely, since English will need to redo the same
recovery against the same file, and the same failure modes are waiting:

- **v1** (`derender_templates.py`): for one representative document per hash, replace each *labeled span's* `text[start:end]` with `{slot}` (descending start order so earlier replacements don't shift offsets), then drop leaky templates via `LEAK_RE`. **Bug**: this only masks spans that are actually PII-labeled. Every *unscored-but-genuinely-variable* field (SPECIALTY, DIAGNOSIS, RELATIVE_RELATION, all DX_* distractor fields) got silently frozen as fixed literal text — confirmed by diffing two documents sharing the same `template_hash` and seeing these exact fields vary between them.
- **v2** (`derender_templates_v2.py`): tried to fix this by also substring-matching known pool values (SPECIALTY list, DIAGNOSIS list, DX_* pools) against the raw text and replacing those too. **New bug, worse than v1's**: sequential `str.replace()` calls against a mutating string corrupted output two ways — (1) short pool values matched as substrings *inside unrelated words* (Dutch "co" matched inside "collega" → `"{DX_ABBREV}llega"`), and (2) later replacement passes matched *inside placeholder tokens already inserted* by earlier passes (`"{DIAGNOSIS}"` containing "OS" got corrupted to `"{DIAGN{DX_ABBREV}IS}"`).
- **v3** (`derender_templates_v3.py`, the one actually used): fixes both bugs by finding every match as a `(start, end, field)` interval against the **original, unmodified** text using word-boundary regex, merging with the real scored spans, resolving overlaps (scored spans win first, then longest-match-wins among the rest), and performing **exactly one substitution pass sorted by start position descending** — the same safe method already proven correct for v1's scored-span-only masking, just applied to the full merged interval set.

**Lesson for English**: do not attempt v1's or v2's shortcuts even though they look simpler — go straight to v3's method (single pass, original-text interval detection, longest-match-wins conflict resolution). It's not extra rigor for its own sake; v1 silently loses real training signal (SPECIALTY/DIAGNOSIS become uneditable dead text) and v2 actively corrupts the recovered templates in ways that are easy to miss on a casual read.

### 2.3 Forking the generator: what carries over unchanged vs. what's real authoring

`pii_table.py` → `pii_table_fr.py`. Kept **unchanged** (Belgian-structural,
not language content): `make_insz`/`valid_insz` (real mod-97 checksum),
`make_riziv`, `make_iban_be`, `luhn_card`, all `fmt_*` formatters, `make_phone`
(Belgian area-code table), `AGE_BANDS`, `NOISE_OPS`, the label-scheme dicts
(`MERGED`/`SPLIT`/`FLAT9`), `audit()`'s statistical logic.

Forked with **real content authoring** (not translation — this needed
independent research, same as it will for English): city/population tables
(real Statbel-weighted, not uniform), street vocabulary, name-origin pools,
medical specialty/diagnosis vocabulary, hospital-naming conventions,
municipality-homograph and clinical-abbreviation hard-negative pools
(explicitly NOT force-translated from Dutch — see 2.4), eponym/distractor
pools, month names (**two separate locations in the file** — easy to miss
one), relation words, honorific/pronoun logic, and two easy-to-miss bits of
language content buried inside otherwise-"structural" functions:
`fmt_address()`'s floor-variant string and `fmt_url()`'s path choices.

### 2.4 Translation and the 5 safety rules that came out of it (`STYLE_RULES.md`)

Full rules file lives at `personal_finetune/french/STYLE_RULES.md` — read it
directly, it's short. Summary, since every one of these is a **grammar
class of bug**, not a one-off typo, and English has its own version of at
least some of them:

1. **Never put a gendered/elidable article directly before a variable-content slot.** French `{SPECIALTY}` includes vowel-initial "ORL" — `"la {SPECIALTY}"` is ungrammatical for it ("la ORL"). Found live in `pii_table_fr.py`'s own `DEMO_TEMPLATE` ("en consultation de {SPECIALTY}" → fixed to "en consultation en {SPECIALTY}"). Safe patterns: no preposition at all, or a preposition that never elides/agrees ("en", "avec").
2. **Same class of bug for `{DIAGNOSIS}`** — the diagnosis pool mixes grammatical gender and vowel/consonant-initial values; any fixed article or agreement-requiring adjective glued directly to the slot breaks on roughly half the pool. Safe: `avec {DIAGNOSIS}`, or colon/label style (`Diagnostic : {DIAGNOSIS}`).
3. **Patient-gender agreement** goes through a dedicated `{PATIENT_NOUN_MARKED}` field (resolves "patient"/"patiente" correctly) — never bolt on a second gendered adjective/participle unless it's truly invariant in both gender and elision.
4. **Never hardcode an honorific before a relative-name slot.** Found *in the original Dutch templates themselves*: a hardcoded "de heer {NAME_RELATIVE}" sitting in the same template as an independently-sampled `{RELATIVE_RELATION}` (Mère/Père/Sœur/Frère/...) — about a third of the time the relation is feminine, directly contradicting the hardcoded masculine honorific. No `{RELATIVE_HONORIFIC}` field exists to fix this properly, so the correct fix is to **drop the honorific before the relative-name slot entirely**, not invent a new field just to patch one contradiction.
5. **Bare unmarked narrative mentions of "patient(e)" as a sentence-subject are NOT caught by automated risky-word scans** (those only flag honorific/pronoun patterns) — must be manually caught during translation and rendered through the proper field, or the exact frozen-narrative problem the field was built to prevent silently reappears by hand.

### 2.5 The "polish and stress-test" bug catalog — chronological, real bugs found after the first "complete" draft

This is the part of the story that matters most for the "we thought we were
done, then found more" pattern — expect the same for English.

**a. `{DIAGNOSIS} {DIAGNOSIS}` stutter (2 templates).** Root cause: the template-recovery script picks ONE representative document per template hash; in these 2 cases, that document happened to have coincidentally sampled the identical value ("ziekte van Von Willebrand" / "maladie de Von Willebrand") for both the `DIAGNOSIS` field and the unrelated `DX_EPONYM` distractor field (the one value present in both pools), and the recovery collapsed them into what looked like one repeated slot. Found by **manually reading rendered documents**, not by any automated check — this is the concrete reason a "logically make sense" manual read-through matters even after automated validation passes.

**b. INSZ/RIZIV → NISS/INAMI mislabeling, across ALL 50 original templates plus `DEMO_TEMPLATE`.** INSZ and RIZIV are the correct **Flemish/Dutch** terms for the Belgian national-registry number and healthcare-provider number — the correct **French** terms for the exact same legal identifiers are **NISS** and **INAMI**. Every translated template had kept the Flemish abbreviation as literal label text instead of translating it. This was NOT caught by manual reading, grammar checks, or span validation — it was caught by the **positional/contextual diversity measurement** (section 2.6): the label text immediately preceding every INSZ/RIZIV span was overwhelmingly the same literal string, which is exactly the "PHONE:-trap" pattern diversity testing exists to catch. **This is the single best argument for running the diversity methodology on English too, not skipping it as "just" a diversity check** — it caught a real authenticity/correctness bug that every other validation layer missed. Fixed by a direct find-and-replace across all templates, then further mitigated (since the fix alone made every document identical again — 100% "NISS"/100% "INAMI") by a new augmentation transform, `xf_id_label_variant`, that randomly swaps in alternate real label phrasings ("N° NISS", "Numéro de registre national", "N° INAMI du prestataire", etc.) at a 25% rate.

**c. Repeated-identical-value in dense tables.** First drafts of the lab-report and pharmacy templates used a single `DX_NUMERIC` Case field to fill *every* numeric cell in a multi-row table — since a Case field's value is sampled once and reused verbatim everywhere it appears in one document (a deliberate design choice, correct for narrative text), every row of a 9-row lab table showed the *identical* filler value, and a pharmacy template showed a time-of-day string ("22h") used as a drug price. Fixed by adding 8 more independently-sampled fields (`DX_NUMERIC_2` through `DX_NUMERIC_9`) and wiring one distinct field per table cell. **Applies directly to English**: any table-shaped genre needs one distinct distractor field per cell, never one field reused across a row/column.

**d. Double-title "Dr dr. X" bug — happened TWICE, independently, in two different templates.** `NAME_DOCTOR`'s Case value already includes a literal `"dr. "` prefix (`f"dr. {surname}"` at generation time). Writing literal `"Dr {NAME_DOCTOR}"` in template prose produces "Dr dr. Delvaux". Found once while building the pharmacy template, fixed there — then **reintroduced independently** while building the radiology template later in the same session, caught again by the same render-and-read smoke test. **Lesson: this is an easy, recurring trap specifically because the prefix lives inside the field value rather than in template prose** — check for it explicitly every time a new template signs off with a doctor's name and title, don't assume "we already fixed this once" means it can't recur.

**e. `ATCD {DX_ABBREV}` literal-collision stutter — same bug class as (a), found much later, silently present in 23 of the original 50 templates the whole time.** `DX_ABBREV`'s distractor pool contains real French clinical abbreviations, and one of the nine entries is literally the string `"ATCD"` (antécédents). Templates that wrote literal `"ATCD {DX_ABBREV}."` produce "ATCD ATCD." roughly 1-in-9 times the field happens to sample that exact value. This was inherited from the Dutch original's "antec. {DX_ABBREV}"-equivalent pattern and went undetected through the entire initial build, the translation pass, and the first validation round — only surfaced while writing a **new** radiology template (which independently made the same mistake) and running its render smoke test. Once found in the new template, a targeted search found it in 22 more of the pre-existing 50. Fixed by removing the redundant literal prefix everywhere (`"ATCD {DX_ABBREV}"` → `"{DX_ABBREV}"`) across the whole bank in one pass. **Lesson for English: any distractor pool that could plausibly contain the same string as a literal prefix already written in template prose is a live risk — grep for `"<the literal prefix> {FIELD}"` across the whole template bank at the end of the build, don't assume the first pass caught every instance.**

**f. A validation-methodology false positive, self-caught.** An early, imprecise check searched the *whole document text* for French articles ("la"/"le"/"du") immediately followed by the first word of a `DIAGNOSIS` value, flagging 39 apparent grammar violations. Rewriting the check to look at the text immediately preceding the **actual span's start offset** (not just anywhere in the document) found 0 real violations — the naive whole-text search was matching coincidental unrelated occurrences of the same words elsewhere in the document. **Lesson: any automated grammar/consistency check must anchor to the real span offset, not do a bag-of-words text search, or it will produce false alarms that waste time (or worse, false confidence if a check that should fire doesn't, because it's anchored wrong).**

**g. A design rule established (not a bug found, but a rule applied proactively after (a) and (b)'s lessons): only ONE physician per document ever carries the single per-case RIZIV/INAMI field.** Case only stores one `RIZIV` value; if a document mentions two different named physicians (e.g., referring doctor + signing doctor, or prescriber + validating pharmacist), attaching the same INAMI number to both would be the same *class* of logical-consistency bug as (a) and (d) — two distinct named individuals sharing one identifier. Every one of the 6 new document genres was written to attach `{RIZIV}` to exactly one doctor and let every other doctor mention go unlabeled with an ID. **Apply this same rule by default in every new English template with more than one named clinician.**

### 2.6 Diversity-testing methodology — why, how, and what it actually caught

This was requested explicitly (not something inferred as "nice to have"),
because LLM/template-generated data can look diverse while following
repetitive structure underneath — the concrete failure mode described was:
if every document has a line like `PHONE:` followed by a number, the model
can learn "anything after PHONE: is a phone number" instead of learning
what a phone number actually looks like. Four measurement types, all
implemented in `personal_finetune/french/validate_diversity_fr.py`:

1. **Lexical diversity**: type-token ratio (whole-corpus and per-document) and distinct-n (1/2/3-gram) on a sampled pool of documents.
2. **Vocabulary overlap**: plain Jaccard overlap of the word sets (train vs. held-out-template eval — expected to be high, since it's the same clinical language; this is NOT a red flag on its own), PLUS a much more informative **template-skeleton overlap**: mask every PII span out to a `<LABEL>` placeholder first, then measure 5-gram overlap between held-out and train skeletons. This is the real test of structural novelty — low overlap means held-out templates are genuinely different prose, not just the same sentences with swapped-in values.
3. **Positional/contextual diversity per PII label**: for every span of a given label, extract the ~12 characters immediately preceding it, count how many *distinct* preceding contexts exist, and what share of all occurrences the single most common context represents. This is the direct, measurable version of the `PHONE:`-trap check — a label stuck at a high top-context-share percentage is exactly the failure mode described. This is the exact methodology that caught bug (b) above (INSZ/RIZIV mislabeling): before the fix, INSZ's top preceding-context share was elevated because "INSZ" (soon corrected to "NISS") appeared as fixed literal text ahead of essentially every occurrence.
4. **Structural diversity counts**: distinct templates, distinct genres (`letter_types`), distinct specialties, distinct organizations/hospitals, distinct PHONE format shapes, distinct DATE format shapes (all computed by collapsing digits to `#` and counting unique shapes).

**Concrete numbers from the final French corpus (56 templates, 12 genres)**, worth using as a rough calibration point for what "reasonably diversified" looks like at this scale, not as a target to hit exactly:
- Per-document TTR ≈ 0.52; distinct-3 (3-gram) ≈ 0.18.
- Jaccard vocab overlap (train vs. held-out) ≈ 0.30; held-out word coverage by train vocab = 1.00 (expected, not concerning).
- **Template-skeleton overlap ≈ 65%** — the one number that stayed stubbornly moderate even after adding genuinely new genres. Honest reading: even "unseen" templates still share the majority of their sentence-level scaffolding with train, because they're all still clinical-register French prose. This is a **known, not fully solved ceiling** — more templates in the *same register* won't move it much; only templates that genuinely diverge in tone/structure would.
- Positional diversity: NAME is the best-generalized label by far (top-context share 8-9%); INSZ/RIZIV/ORGANIZATION/PHONE sit in a moderate 20-40% band even after the `id_label_variant` fix improved them from a worse starting point (INSZ went from ~33% to ~26-32% depending on corpus slice). **These four labels are the ones to watch first in any real eval run.**

**Recommendation for English**: build the equivalent `validate_diversity_en.py` from day one (don't wait for a "polish" phase to bolt it on) — it is the check most likely to catch a real authenticity bug (like the NISS/INAMI mislabeling) that no other validation layer will find.

### 2.7 Grounding extraction-noise in the REAL production pipeline, not guesswork

The team's actual PDF-text-extraction code (a PyMuPDF-based "recursive
XY-cut" algorithm — segments a page via alternating vertical/horizontal
whitespace-gap cuts, detects genuine ruled tables via `page.find_tables()` +
`table.to_markdown()`, joins same-line text fragments with a naive
`"".join()` with no gap check) was obtained directly from the team
(`personal_finetune/french/extract_pdf_text.py`, saved verbatim) and run
against the 5 real reference PDFs
(`TamerBERT/TamerBERT/org_data/*.pdf`), diffing its raw output against the
known reference text. This found real, empirically-confirmed failure modes,
not hypothetical ones:
- Pre-redaction placeholder tokens leak through in the raw extraction (`[ADRES]`, `[TELEFOON]`, `PATIËNT B`).
- A confirmed **mid-word splice**: an address value gets inserted in the middle of an unrelated word (`p[ADRES]nd`) when the XY-cut heuristic misjudges a column boundary.
- A confirmed **3-column-header-as-garbled-table bug**: a real header region (patient name / responsible / date) gets misdetected as a ruled table, producing a garbled markdown table with the patient's name literally **tripled** across three cells and stray `<br>` tag leakage.
- A confirmed **DATE-block relocation**: on one document, the encounter date block gets physically relocated to the bottom of page 1, after an unrelated table, by the extraction algorithm.

Two augmentation transforms were built directly from these confirmed
patterns (`xf_header_table_garble`, `xf_midword_splice` in
`augment_fr.py`), plus a dedicated hard-eval set
(`build_hard_extraction_eval_fr.py`) that maps each of the 5 real letter
templates to its **own specific confirmed noise type** (not noise applied
uniformly/randomly) — 75 documents total.

**For English**: get the same `extract_pdf_text.py` script (it's
language-agnostic — it operates on PDF layout geometry, not text content)
and run it against whatever real English-language reference PDFs exist for
this project, if any do. If none exist (worth confirming explicitly — see
2.8), the fallback is to reuse the SAME confirmed failure-mode *shapes*
(header-region table misdetection, mid-word splice, block relocation) since
those are properties of the extraction algorithm's geometry heuristics, not
of Dutch or French text specifically — but say so explicitly in your own
handoff notes as an inferred-from-mechanism assumption, not a
real-document-confirmed one, the same way this document distinguishes the
two.

### 2.8 A research finding worth knowing before assuming more real documents exist

Background research (dispatched explicitly to check) confirmed: **no
additional real reference documents exist beyond the 5 known PDFs**
(`TamerBERT/TamerBERT/org_data/*.pdf`). Also worth knowing: "HealthOne
Nova" — the name used in casual conversation for this document set —
appears to be **only a filename label**, not a confirmed real EHR
vendor/product; the actual hospital name printed **inside** all 5

"HealthOne Nova" is a real system to research or match conventions

real English-language reference documents anywhere in the repo or from the
team?) rather than assuming either way.

### 2.9 New document genres — research-grounded, not guessed

The original build only ever produced one document SHAPE: a narrative
clinical letter (5 sub-types: consultation/discharge/urgent/follow-up/
technical-exam report — all still "Dear colleague"-style prose). Per the
lesson in Part 1 item 5 (narrow structural diversity was the real OOD root
cause for Dutch), 6 new, structurally distinct genres were added, each
grounded in actual research into real Belgian conventions rather than
invented from general knowledge — **this research was dispatched as an
explicit task** (a background research agent using web search against
INAMI/SPF Santé/BELAC/professional-order/hospital-institutional sources,
explicitly instructed to avoid any site that might host real patient
records and to distinguish confirmed-regulatory facts from inferred
conventions):

| Genre | Grounding / confidence | What makes it structurally distinct |
|---|---|---|
| **Lab report** (`genre_lab_report_fr`) | General lab-report convention (panel names, reference ranges) — medium confidence | Genuine pipe-delimited markdown tables (Hématologie / Biochimie panels), matching what the real extraction pipeline's `table.to_markdown()` produces for a correctly-detected table |
| **Pharmacy dispensing record** (`genre_pharmacy_fr`) | CNK code and A/B/C reimbursement categories are **confirmed real** (INAMI/AFMPS regulatory facts); exact label layout inferred | Compact transaction-record format; introduced CNK (Code National) as a new alphanumeric hard-negative |
| **Radiology report** (`genre_radiology_fr`) | **High confidence** — Motif/Indication→Technique→Résultat→Conclusion is documented as a *mandatory* (order-flexible) structure in real Belgian academic radiology teaching material | Fixed section-header narrative, not letter or table |

| **Prescription proof** (`genre_prescription_fr`) | **Medium confidence** — Belgium's Recip-e mandatory e-prescribing and the printed "proof of e-prescription" A4 sheet are confirmed regulatory facts; exact RID/field wording inferred | Barcode-linked proof-sheet format, deliberately WITHOUT a CNK (assigned at dispensing, not prescribing) |
| **Discharge medication schema** (`genre_discharge_meds_fr`) | **Medium-high confidence** — "schéma de médication" is a confirmed real INAMI-defined concept; exact column layout inferred | A third genuine table genre, serving a different purpose (full regimen carry-forward) than the pharmacy record (one transaction) |

**Known, stated limitation carried forward honestly**: each of these 6
genres currently has exactly **ONE** template skeleton (vs. 50 skeletons
for the letter genre) — meaning PII-value diversity within each new genre
is excellent (130+ renders each) but structural/wording diversity within
each genre is minimal. If a QA tester supplies a differently-worded lab
report or prescription, the model has only ever seen one shape to
generalize from. **For English, budget for at least 2-3 skeletons per new
genre from the start if time allows**, rather than repeating this
single-skeleton shortcut.

Two real bugs (items 2.5d and 2.5e above) were caught specifically while
building these new genres, both via the same method: **write the template,
render it 10-30 times with different random seeds, and actually read the
output** — not just check that spans align, but read the prose for
sense. Do this for every new English template too, it's cheap and it's
what caught both bugs.

### 2.10 OOD and perturbation coverage — separate from training augmentation, eval-only

Two distinct things, easy to conflate — keep them conceptually separate for
English too:
- **`augment_fr.py`** transforms are baked INTO the training pool (`train_augmented_fr.jsonl`) — the model trains on them.
- **OOD battery + perturbation sweep are EVAL-ONLY** — hand-authored or systematically-perturbed documents the model never trains on, used purely to measure generalization.

The Dutch track built up an OOD catalog across **6 rounds** (v1 through v6,
~45 hand-authored categories total, covering things like name diacritics,
adversarial casing, partial redaction, non-medical false-positive probes,
numeric hard-negative ID types, sliding-window boundary crossing, and more
— the authoritative source is the actual `ood_stress_test_v2` through
`ood_stress_test_v6` directories in the repo, read them directly rather
than relying on a secondhand list). French had only ported round v1's
~16-17 categories before this session. This gap was closed by authoring
**15 new French documents** covering the previously-missing v2-v6
categories (`ood_stress_test_fr/build_ood_set_fr_v2.py` /
`ood_docs_fr_v2.jsonl`) — multi-word surnames, partial redaction, numeric-ID
hard negatives, an approximate sliding-window boundary probe, quoted/
forwarded email, foreign-phone scope probe, minimal-document floor check,
homoglyph substitution, email-header validation, organization+VAT hard
negative, three letterhead-adjacency structural variants, honorific
generalization, and an all-caps eval instance — plus a **640-document
systematic perturbation sweep** (`perturbation_sweep_fr.py`, 8 transforms:
upper/lower/title casing, whitespace jitter, trailing-period stripping,
NBSP substitution, 60%/85% truncation, applied across 80 sampled source
documents).

**For English**: read the real Dutch v1-v6 directories directly (don't
re-derive from this summary) to decide which categories genuinely need
fresh, English-specific authoring (hard negatives like homographs and
abbreviations are language-specific and must be researched fresh, not
translated) versus which are purely mechanical and can be ported with the
same transform code (the perturbation-sweep transforms are
language-agnostic position/offset mechanics — reuse them as-is, same as
French did).

### 2.11 The full validation suite — run all three, in this order, after ANY template-bank change

Three scripts, each catching a different class of problem. All three must
show 0 errors before treating a dataset as ready, and **all three must be
re-run after adding/editing even one template**, not just at the end:

1. **`validate_all_fr.py`** — mechanical correctness. Per labeled span: in-bounds, non-empty, `text[start:end]` actually equals the span's recorded text, label is in the expected set, no duplicate IDs within a file. Also a cross-file ID-collision check across every file that carries an `id` field. This is the baseline "did the code do what it was supposed to" check — catches offset-math bugs, not content bugs.
2. **`validate_consistency_fr.py`** — logical/narrative correctness, 4 checks: (a) Case-level invariants across thousands of freshly-generated cases (sex/gender/pronoun/honorific/diagnosis-specialty pairing all agree with each other); (b) every recurring slot in a rendered document has exactly one consistent value throughout that document; (c) the AGE numeral is stable within a document (no "42 years old" in paragraph 1 and "45 years old" in paragraph 3); (d) every span in the AUGMENTED file is still in-bounds after transform-remapping. This is the check that would have caught (a) the DIAGNOSIS/DX_EPONYM stutter and (c) the DX_NUMERIC-repeated-in-table bug, if it had existed before those were found by manual reading — build it early for English, not after finding the same bugs the slow way.
3. **`validate_diversity_fr.py`** — the 4-part methodology in section 2.6. This is the one that caught the INSZ/RIZIV mislabeling that nothing else caught. Not optional.

Beyond the three scripts, a cheap but valuable extra step used repeatedly
in this project: **render every new template 10-30 times with different
seeds and manually read a sample of the output.** Every genuinely
narrative/logical bug found in this whole project (2.5a, 2.5d, 2.5e) was
caught this way, not by any automated script — automated checks catch
what they're explicitly built to check for; reading catches everything
else.

## PART 4 — English-specific considerations: resolve these BEFORE writing code

Flemish (Dutch track) and Walloon (French track) both map onto a real
Belgian linguistic community with its own region, cities, and native
population. **English does not.** Nobody's ethnic-native-language community
in Belgium is "English" — English speakers in Belgium are functionally
expats, EU/NATO institution staff, international-school families, and
multinational-company employees, heavily concentrated in Brussels
specifically. This breaks several assumptions the French/Dutch generator
design leans on, and none of them have an obviously-correct answer baked
into the existing pipeline — **surface these to whoever's driving the work
and get them explicitly resolved before committing code**, the same way
"Belgian French, not France-French" had to be explicitly confirmed before
any French content was written (2.1):

1. **Geography**: model English-track documents as Brussels-concentrated (matching where the real anglophone population actually lives) or nationally distributed (any Belgian hospital could in principle issue an English letter)? The French generator's population-weighted `WALLOON_CITIES` table (real Statbel weights) has no obvious English analogue — there's no "Anglophone region of Belgium" to pull population data for.
2. **Name-origin / demographic stratification**: the Dutch and French generators stratify by `name_origin` to model the REAL immigrant-origin composition of the *native* population being treated — an explicit fairness/differential-recall measurement tool. For English, the population being modeled is fundamentally different: an expat/international community, not a native-population-with-immigrant-minorities. A realistic mix is something like UK/Ireland, US, other-EU-staff-using-English-as-lingua-franca, and Anglophone-Africa/Asia (Nigeria, India, etc.) — NOT the same categories used for French/Dutch. Rebuild this around what the English-speaking population in Belgium actually looks like; don't reuse the French/Dutch weight structure.
3. **Street/address naming**: Belgium does not have "English street names." A real English-language medical letter about a Brussels patient would still show the ACTUAL Belgian street name (French or Dutch — Brussels streets are officially bilingual, e.g. "Rue de la Loi / Wetstraat"; elsewhere it's whichever regional language is official). **Do not invent an English-style street-naming convention** — reuse real Belgian street names/patterns (borrow from the French or Dutch generator depending on where in Belgium the case is set) with English prose around them.
4. **Spelling/register convention**: British vs. American English spelling (e.g. "oesophagitis" vs. "esophagitis", "anaemia" vs. "anemia") is a real decision, not a detail — EU-institution and Belgian-international-school English strongly skews British/international convention, not American. Recommend British/international spelling as the default, but state this as an explicit decision, not a fallback you back into.
5. **Letter register**: should generated English read like a native British/American clinical letter, or like "Belgian clinical correspondence written in English by a Belgian doctor" (Belgian phrasing/structure conventions, English vocabulary — arguably the MORE realistic register here, since the underlying institutions and doctors are Belgian)? Decide and document this before translating any templates — it changes how the translation-safety-rules pass (2.4-equivalent) gets done.

**One place English is actually simpler than French, worth knowing before
you assume everything gets harder**: French `son`/`sa` (his/her) agree with
the GENDER OF THE POSSESSED NOUN, not the possessor's sex, which broke a
naive per-case `PRONOUN_POSS` field and forced it to be dropped entirely for
French (see `pii_table_fr.py`'s docstring). English `his`/`her` agree with
the POSSESSOR's sex, exactly like Dutch's `zijn`/`haar` — a simple per-case
`PRONOUN_POSS` field works fine for English, no special-case needed. Same
for the patient noun: English "patient" has no separate masculine/feminine
form at all (unlike French patient/patiente or Dutch patient/patiënte) — no
`PATIENT_NOUN_MARKED`-equivalent distinction is needed for English.
