# Belgian PII detection — English & French data tracks: handoff

This document describes **what exists today** for the English and French
PII-detection data tracks: what the data looks like, how it was generated,
how it was validated, and what's known to still be imperfect about it. Both
tracks' **data-generation phase is complete and fully validated** — 0 errors
across every validator, on the full corpus, as of 2026-08-19. Neither track
has started Kaggle fine-tuning yet; that's the next phase, out of scope
here.

Read this if you're picking up either track to: fine-tune a model on the
data, extend the data further (new genres, more languages), or debug
something that looks wrong in a rendered document. Section 8 lists what's
still genuinely unfinished — read that before assuming a gap is a bug
nobody noticed.

---

## 0. Project context

This repo (`End-to-End-PII-v2`) fine-tunes a RoBERTa-family model **per
language** to detect PII (names, dates, addresses, national ID numbers,
phone numbers, etc.) in synthetic medical documents. Training data is
entirely synthetic — generated by a Python script, not real patient
records. Architecture decision (settled, don't re-litigate): one
monolingual model per language, not a shared multilingual model — a
published study (arXiv:2412.10918) got F1 0.95–0.98 training separate
experts for French/English/Romanian/Spanish/German, beating GPT-4o;
general/zero-shot multilingual PII models cap around F1 0.6 regardless of
architecture.

**Both English and French tracks are Belgian**, not UK/US-English or
France-French. Belgian-national identifier formats — INSZ (national
registry number, real mod-97 checksum), RIZIV (healthcare-provider number),
IBAN "BE" prefix, Belgian phone area codes — are shared, unchanged, across
every language track. Only the surrounding prose and the **label text**
used for each identifier changes with the document's language (French says
"NISS", English says "National Registration No." or a sampled variant — see
§3.4); the underlying **JSON span label stays `INSZ`/`RIZIV` in every
language**, always.

**Status as of 2026-08-19:**
| Track | Base model | Data-gen phase | Kaggle fine-tune |
|---|---|---|---|
| Dutch | `CLTL/MedRoBERTa.nl` | Shipped: `pii-medroberta-nl-v2`, indist F1 0.988, OOD F1 0.803 | Done |
| French | `almanach/camembert-bio-base` | **Complete, 0 errors** | Not started |
| English | `obi/deid_roberta_i2b2` | **Complete, 0 errors** | Not started |
| Spanish | `PlanTL-GOB-ES/bsc-bio-ehr-es` | Not started | Not started |

Infra rules that apply to every track (learned the hard way once):
Kaggle downloads always need `--file-pattern` (it's a regex, not a glob).
The D: drive has a real recurring hardware fault (`OSError: [Errno 22]`) —
route around it, don't debug it as code. Model checkpoints/MLflow push
directly from Kaggle via a companion kernel, never touch the local disk.
`git push` is blocked by the permission classifier here — hand the command
to the user.

## 1. What a rendered document actually looks like

Every document is a JSON object: `{"id", "text", "spans", "meta"}`. A span
is `{"start", "end", "text", "label", "slot", "subject", "fmt"}` — `label`
is the trained NER category, `slot` is the internal field name (multiple
slots collapse into one label — e.g. `NAME_PATIENT`/`NAME_DOCTOR`/
`NAME_RELATIVE` all collapse to `NAME`), `subject` marks whose PII it is
(patient/provider/other), `fmt` records which format variant was sampled
(useful for per-format recall analysis later).

Real example, `train_en.jsonl` (a `discharge_medication_schema` genre doc):

```
UZ Rivierenland
DISCHARGE MEDICATION SCHEMA
Chemin du Moulin 209
T +32 57 07 92 26

Patient: Émilie Halleux
National ID89.10.12-350.65
Date of birth: °12/10/1989

Responsible physician: Dr Chikezie
NIHDI No.61283214030

Discharged on: 17/05/2026

| Medicine | Dosage | Frequency | Indication |
|---|---|---|---|
| Paracetamol 1 g | 300 IU/ml 1.5ml | 25,000 IU | epilepsy in remission |
| Ozempic 1 mg | 1x/week | 100u/ml 3ml | Bechterew's disease |

This schema replaces any prior treatment as of 6/8. Tx.
État général conservé.

To be handed to the GP and the pharmacist.

Validated on 17 May 2026 by Dr Okeke.

UZ Rivierenland
https://uzrivierenland.be/contact
```

Its first few spans: `ORGANIZATION` "UZ Rivierenland" (slot `ORGANIZATION`),
`ADDRESS` "Chemin du Moulin 209" (slot `STREET`, subject `patient`), `PHONE`
"+32 57 07 92 26" (fmt `intl`), `NAME` "Émilie Halleux" (slot
`NAME_PATIENT`), `INSZ` "89.10.12-350.65" (fmt `dotted`), `DATE`
"°12/10/1989" (slot `DOB`, fmt `masc_ordinal_dd/mm/yyyy`).

Note the deliberate hard negatives around the table: "300 IU/ml 1.5ml",
"25,000 IU", "1x/week" are clinical-looking numeric strings that are **not**
labelled — they exist so the model learns numeric shape alone isn't enough
to call something PII. "Bechterew's disease", "Paracetamol", "Ozempic" are
real medical vocabulary, also unlabelled.

### 1.1 The 10-label taxonomy (identical across Dutch/French/English)

`NAME`, `INSZ`, `RIZIV`, `DATE`, `ORGANIZATION`, `AGE`, `ADDRESS`, `PHONE`,
`URL`, `EMAIL`. This is a **span category**, independent of the document's
language — an English document literally saying "National Registration
No. 71051234567" and a French document saying "NISS 71051234567" both tag
the number `INSZ`. `EMAIL` only appears via the `xf_email_header`
augmentation transform in both tracks — the base translated letter
templates carry zero `EMAIL` spans in either language (this gap is closed
downstream, see §7).

## 2. Architecture: shared vs. per-language

Both `pii_table_en.py` and `pii_table_fr.py` are forks of the same Dutch
original (`pii_table.py`), and of **each other** in French's case — English
forked the already-hardened French file specifically to inherit its
bugfixes for free.

**Kept structurally identical across all three languages** (Belgian
national facts, not language content): `make_insz`/`valid_insz` (real
mod-97 checksum), `make_riziv`, `make_iban_be`, `luhn_card`, all `fmt_*`
formatters, `make_phone` (Belgian area-code table), `AGE_BANDS`,
`NOISE_OPS`, the label-scheme dicts (`MERGED`/`SPLIT`/`FLAT9`/`SUBJECT`),
`render()`'s placeholder-substitution mechanics, `audit()`'s statistical
logic.

**Forked with real content per language** (each needed independent
research, not translation): city/population tables, hospital-naming
pools, name-origin pools, medical specialty/diagnosis vocabulary,
municipality-homograph and clinical-abbreviation hard-negative pools,
street vocabulary, month names, relation words, honorific/pronoun logic.

### 2.1 Locked-in design decisions per track

**French — Belgian French (Walloon), not France-French.** Geography scoped
to Wallonia + Brussels only (`WALLOON_CITIES`, 45 real cities across every
Walloon province + Brussels-Capital — deliberately **no Flemish cities**,
since Flanders isn't Francophone territory). 5 name-origin pools modeling
the real immigrant-origin composition of Wallonia's native population:
`walloon` (w=0.60), `southern_european` (0.15), `maghrebi` (0.10),
`central_african` (0.05), `eastern_european` (0.10).

**English — nationally distributed, expat/international demographic.**
Unlike French/Dutch, there's no native "Anglophone region" of Belgium to
model — English speakers are functionally expats, EU/NATO staff,
international-school families. Locked-in decisions (resolved via explicit
Q&A before any content was written):
- **Geography: nationally distributed** — `BELGIAN_CITIES`, 57 real cities
  spanning Flanders + Wallonia + Brussels, all 10 provinces represented.
- **Demographics: expat/international mix, PLUS native Belgian names** (a
  mid-build correction from an earlier "expat-only" draft) — 7 origin
  pools: `flemish` (0.14), `walloon` (0.11), `uk_ireland` (0.19), `us`
  (0.10), `other_eu_staff` (0.22), `anglophone_africa` (0.13, currently
  Nigeria-focused), `anglophone_asia` (0.11, currently India-focused).
- **Street naming**: reuses real Belgian street vocabulary (French/Dutch,
  region-matched) — there's no "English street name" convention to invent.
- **Spelling**: British/international ("anaemia", "oesophagitis").
- **Register**: "Belgian doctor writing in English" — Belgian
  phrasing/structure, English vocabulary, not native British/American
  clinical-letter style. Some resulting phrasing is deliberately
  non-native-sounding (e.g. "a 75 years old patient" instead of "a
  75-year-old patient") — this is in-character for the persona, not a
  grammar bug, and it's used consistently across the whole template bank.
- **English needs no `PATIENT_NOUN_MARKED`-equivalent** (English "patient"
  has no gendered form) and **`PRONOUN_POSS` is a simple per-case field**
  (English his/her agrees with the possessor's sex, like Dutch) — genuinely
  simpler than French, where `son`/`sa` agree with the POSSESSED noun's
  gender instead, forcing that field to be dropped entirely for French.

### 2.2 Label-text vs. label-taxonomy (the distinction that caused French's worst bug)

The literal words a document *displays* for INSZ/RIZIV are researched,
real, per-language administrative terms — not what the JSON span is
*labelled*. French templates show "NISS"/"INAMI"; English templates show
"National Registration No."/"NIHDI No." (both confirmed via real Belgian
federal-government English-language usage, not dictionary translation).
The JSON span label is `INSZ`/`RIZIV` in **every** language, always. French
originally shipped all 50 templates with the **Flemish** abbreviations
("INSZ"/"RIZIV") as literal label text instead of the French terms — a bug
that survived translation, manual reading, and an early validation round,
caught only by the diversity-measurement methodology (§7.3). This exact
risk was checked proactively before English's templates were written.

## 3. How the data was generated

### 3.1 Template recovery

The original ~50 Dutch templates only survive as rendered output
(`TamerBERT/TamerBERT/train.jsonl`, 6,417 documents, 69 `template_hash`
values). Recovering the masked template text from it went through 3
iterations before landing on a correct method — the two failed attempts are
worth knowing if this ever needs re-running: **v1** only masked
PII-labelled spans, silently freezing every unscored variable field
(SPECIALTY, DIAGNOSIS, distractor pools) as dead literal text. **v2** tried
to fix that with sequential `str.replace()` calls against pool values,
which corrupted output via substring collisions (Dutch "co" matching inside
"collega") and self-collision (a replacement matching inside a
just-inserted placeholder). **v3** (the one used) finds every match as a
`(start, end, field)` interval against the **original, unmodified** text,
merges with real scored spans, resolves overlaps, and substitutes in one
pass sorted by start position descending. Both English and French reused
this same recovered `recovered_templates_nl_v3.jsonl` — this step wasn't
repeated per language, since the recovery source doesn't change.

### 3.2 Translation

Templates were translated (not machine-translated verbatim — each pass
applied language-specific grammar-safety rules, see `french/STYLE_RULES.md`
for the full 5-rule list) into 50 letter-genre templates per language,
covering 5 letter sub-types (consultation, discharge, urgent-care,
follow-up, technical-exam report). Every render was smoke-tested (10–30
seeds, read the actual output) before being counted as done — this is what
catches narrative/logical bugs no automated check would (double-titles,
stutters, sense).

### 3.3 The `Case` / `render()` architecture

`build_case()` samples one coherent synthetic person + encounter per
document (name, sex, age, all dates, address, phone, hospital, diagnosis,
etc.) into a `Case` dataclass. `render(template, case, scheme)` fills every
`{FIELD}` placeholder in the template text from the matching `Case`
attribute via regex, and emits a labelled span **only** for fields present
in the `scheme` dict passed in — non-PII fields (like the new
`INSZ_LABEL`/`RIZIV_LABEL`, §3.4) still get substituted into the text but
never produce a span. The same `Case`/`render()` mechanics are byte-
identical across Dutch/French/English; only the content pools differ.

### 3.4 Recent fix: INSZ/RIZIV label-text is now sampled per-case, not hardcoded

English originally hardcoded the literal "National Registration No." before
every `{INSZ}` in all 50 templates — 100% consistent, which the diversity
validator immediately flagged (§7.3) as a positional-rigidity risk. This
was first patched via an augmentation transform (`xf_id_label_variant`,
swapping in alternate phrasings for a fraction of documents), but since
augmentation only *adds* transformed copies on top of unmodified originals,
that could only get INSZ's positional diversity down to 63.9% — still far
worse than French's naturally-occurring 28.4%.

**Fixed at the root** (2026-08-19): `pii_table_en.py` now has
`INSZ_LABEL`/`RIZIV_LABEL` as per-case sampled fields (`LABEL_POOL_INSZ` /
`LABEL_POOL_RIZIV`, 5 phrasing variants each — "National Registration
No.", "NRN", "Reg. No.", "National ID", "ID No." / "NIHDI No.", "N° NIHDI",
"Provider ID", "INAMI/NIHDI No.", "Physician ID"), and all 56 templates
render `{INSZ_LABEL}{INSZ}`/`{RIZIV_LABEL}{RIZIV}` instead of a hardcoded
literal. This applies the variety to **100% of the corpus from
generation**, not a fraction of augmented copies. The now-redundant
`xf_id_label_variant` transform was removed from `augment_en.py` entirely.
Result: INSZ positional top-context share dropped to **17.3%**, RIZIV to
**17.6%** — both now *better* than French's own numbers (28.4% / 20.8%).

### 3.5 Vocabulary pools — sizes and how they were expanded

| Pool | English | French |
|---|---|---|
| Cities | 57 (all 3 regions, all 10 provinces + Brussels) | 45 (Wallonia + Brussels only, by design) |
| Hospital identities (standalone + prefix×stem combos) | 43 standalone (Flemish share fixed: was 7/35, now 15/43) + 7×23 combinable | 83 standalone (already deep) + 6×11 combinable |
| Names (male / female / surnames) | 125 / 122 / 132 | 83 / 82 / 94 |
| Street vocabulary | 25 stems × 17 suffixes (Flemish) + region-matched French/Dutch street types | same, shared with Dutch/French |

All city/hospital additions are **real, web-search-verified facts**, not
fabricated — including catching that Eupen (a candidate Wallonia-region
city) is actually the capital of Belgium's German-speaking Community
(German, not French, is the official/legal language there), so it was
added to English's nationally-distributed pool only, never to French's —
the same logic that already excludes Flemish cities from French. Name-pool
expansions (common-knowledge naming data per origin community) weren't
web-verified, unlike the geographic/institutional facts.

**Known, not-yet-addressed gap**: `anglophone_africa` and
`anglophone_asia` are currently Nigeria-only and India-only respectively,
despite the design intent naming "Anglophone Africa/Asia" more broadly
(Ghana, Kenya, Philippines, Pakistan, etc. are all real, common source
countries for English-speaking Belgian expats). This wasn't fixed in this
round — flagged here as a real, scoped follow-up, not silently left
unexplained.

## 4. Document genres (12 per track, identical count)

5 letter sub-types (~10 templates each) + 6 non-letter genres + the
untyped demo/default = 56 templates total, **identical count in both
tracks**. The 6 non-letter genres exist because the Dutch track's own
post-mortem found narrow *structural* diversity (not field-format
diversity) was the real root cause of its OOD ceiling — both English and
French built these from round 1 rather than discovering the gap the slow
way a second/third time.

| Genre | Grounding | What makes it structurally distinct |
|---|---|---|
| Lab report | Medium confidence (general convention) | Genuine pipe-delimited markdown tables (Haematology/Biochemistry panels) |
| Pharmacy dispensing record | CNK code + A/B/C reimbursement categories confirmed real (INAMI/AFMPS) | Compact transaction record, introduces CNK as a numeric hard negative |
| Radiology report | **High confidence** — Indication→Technique→Result→Conclusion is a documented mandatory structure | Fixed section-header narrative |
| Sick-leave certificate | **High confidence** — modeled directly on the real public INAMI blank form | Genuinely form-shaped: two-part patient declaration / "MEDICAL CONFIDENTIAL" physician section, with `[X]`/`[ ]` checkboxes |
| E-prescription proof | Medium confidence (Recip-e mandate confirmed; exact field wording inferred) | Barcode-proof-sheet format, deliberately no CNK (assigned at dispensing, not prescribing) |
| Discharge medication schema | Medium-high confidence ("schema de médication" is a real INAMI concept) | Second genuine table genre, full-regimen carry-forward (vs. pharmacy record's single transaction) |

**Known, honestly-stated limitation, both tracks**: each of these 6 genres
has exactly **one** template skeleton (vs. ~10 skeletons for the letter
genre) — PII-value diversity within each is excellent (130 renders each)
but wording/structure diversity is minimal.

## 5. Augmentation

`augment_{en,fr}.py` takes `train_filtered.jsonl` (documents from the
train-pool templates only, after the held-out-template split) and produces
`train_augmented_{en,fr}.jsonl` by **adding** transformed copies on top of
the unmodified originals — never replacing them. Shared transform
mechanics (position/offset math, language-agnostic): `xf_casing`,
`xf_ocr_noise`, `xf_mojibake`, `xf_diacritic_honorific`, `xf_inline_mention`,
`xf_org_context`, `xf_email_header`, `gen_non_medical`, plus two
**real-extraction-pipeline-grounded** transforms — `xf_header_table_garble`
and `xf_midword_splice` — built from actually running the team's production
PyMuPDF-based extraction algorithm against the 5 real reference PDFs and
diffing its output against known-correct text (confirmed failure modes: a
3-column header misdetected as a ruled table; an address value spliced
mid-word into an unrelated word). French additionally keeps
`xf_id_label_variant`; English's was removed (§3.4).

**Final counts**: `train_augmented_en.jsonl` = 10,463 docs (5,265 original +
5,198 augmented). `train_augmented_fr.jsonl` = 11,668 docs (5,265 + 6,403 —
larger because French still runs the id-label-variant transform on top of
the others).

## 6. Full pipeline, in order

```
recovered_templates_nl_v3.jsonl (shared source, both languages)
  -> translate + smoke-test  -> translated_templates_{en,fr}.jsonl (50)
  -> + 6 new-genre templates -> translated_templates_{en,fr}.jsonl (56)
  -> emit_dataset_{en,fr}.py -> train_{en,fr}.jsonl (7,280 docs)
  -> prep_data_{en,fr}.py    -> tamerbert_data_{en,fr}/{train_filtered, eval_indist, eval_heldout_templates}.jsonl
  -> augment_{en,fr}.py      -> train_augmented_{en,fr}.jsonl
  -> build_eval_real_{en,fr}.py            -> eval_real_{en,fr}.jsonl
  -> build_hard_extraction_eval_{en,fr}.py -> eval_hard_extraction_{en,fr}.jsonl
  -> perturbation_sweep_{en,fr}.py         -> perturbation_sweep_{en,fr}.jsonl
  -> ood_stress_test_{en,fr}/build_ood_set_{en,fr}[_v2][_v3_novel_vocab].py -> ood_docs_*.jsonl
```

`prep_data_{en,fr}.py` splits by `template_hash` (20% of templates held out
entirely, seed 42) — this is the real generalization test, not just a
random document split. It also filters out any template containing a
literal format-hint leak (`DD-MM-YYYY`, `MM/YYYY`, `JJ-MM-AAAA`,
`MM/AAAA`) — a real Dutch bug (19-of-69 templates) this filter exists to
catch permanently; found 0 leaky templates in either language's current
bank.

The 5 real-letter-derived templates (the only genuine ground truth this
project has — the actual HealthOne Nova PDFs the whole bank was originally
derived from) land in the **train pool**, not the held-out split, in both
languages — 650 documents each. `eval_real_{en,fr}.jsonl` exists
specifically to still get real-letter-grounded eval signal despite that:
it renders 50 fresh documents from those same 5 templates using a doc-ID
range the main generation never touches, so the specific PII *values* are
guaranteed unseen even though the template *shape* was trained on.

## 7. Validation — what was run, and what each check catches

Every one of these was re-run after every change in this session; all
currently report **0 errors**, on the full corpus, for both languages.

### 7.1 `validate_all_{en,fr}.py` — mechanical correctness
Per span: in-bounds, non-empty, `text[start:end]` actually equals the
recorded span text, label is in the expected 10-label set, no duplicate IDs
within a file. Cross-file ID-collision check across every file carrying an
`id`. Run across `train`, `train_augmented`, `eval_real`,
`eval_hard_extraction`, and all three `tamerbert_data_*` split files —
**7 files, 0 errors, both languages.**

### 7.2 `validate_consistency_{en,fr}.py` — logical/narrative correctness
Four checks: (a) case-level invariants on 5,000 fresh cases (sex/gender/
pronoun/honorific/diagnosis↔specialty all agree); (b) every recurring
slot in a rendered document has exactly one value throughout; (c) the AGE
numeral is stable within a document; (d) every span in the augmented file
is still in-bounds after transform-remapping. Date ordering
(`DATE_HISTORY < DATE_ENCOUNTER <= DATE_VALIDATION`) is proven here **by
construction** from the sampling arithmetic — §7.5 below verifies it
**empirically**, on real rendered dates, as an extra layer.

### 7.3 `validate_diversity_{en,fr}.py` — is it actually diverse, or just varied-looking?
Four measurements: lexical diversity (TTR, distinct-n); vocabulary overlap
(Jaccard, plus **template-skeleton overlap** — mask PII to `<LABEL>` and
measure 5-gram overlap between held-out and train skeletons, the real test
of structural novelty); **positional/contextual diversity per label** — for
every span, look at the ~12 characters immediately before it, and measure
what fraction of all occurrences share the single most common context (the
"PHONE:-trap" check: if every phone number follows the identical literal
text, the model can learn "anything after this phrase" instead of learning
what a phone number looks like); structural counts (distinct templates,
genres, specialties, orgs, PHONE/DATE format shapes).

**This is the single check that caught French's INSZ/RIZIV mislabeling**
(§2.2) and English's INSZ positional-rigidity issue (§3.4) — both slipped
past every other validation layer. Current final numbers:

| Label (post-augmentation) | English | French |
|---|---|---|
| INSZ top-context share | 17.3% | 28.4% |
| RIZIV top-context share | 17.6% | 20.8% |
| Template-skeleton overlap (held-out vs. train) | 65.3% | 65.2% |

Template-skeleton overlap ~65% is a **known, unsolved ceiling** in both
languages — even "unseen" templates share majority sentence-level
scaffolding since they're all still clinical-register prose in the same
language. More templates in the same register won't move this; only
genuinely different tone/structure would.

### 7.4 `validate_translated_templates_en.py` — English-only, template-bank-level
Static checks (valid placeholders, adjacent-duplicate stutters, one-doctor-
one-ID, no literal "Dr" before a doctor field, no hardcoded honorific
before a relative field) plus a 30-seeds × 56-templates render test (1,680
renders). **0 errors.** French has the equivalent rigor split across its
own translation-batch `validate()` functions plus manual smoke-testing.

### 7.5 `validate_dates_deep.py` — NEW, deeper date-specific validation (2026-08-19)

Requested explicitly as an extra pass beyond §7.2's construction-only proof
and §7.1's offset-only bounds check (neither of those verifies a date
span's *content* is actually a real, unambiguous calendar date). This
script:
1. Parses **every** DATE span in the full (unsampled) `train_{en,fr}.jsonl`
   against the exact format set `fmt_date()` can produce, flagging any that
   fail to parse under any known format or resolve to an impossible
   calendar date (Feb 30, month 13, etc.).
2. Re-derives `DATE_HISTORY < DATE_ENCOUNTER <= DATE_VALIDATION` using
   **parsed date objects**, across the full 7,280-document corpus (not the
   3,000-doc sample §7.2 uses).
3. Cross-checks DOB against the document's own AGE span: DOB not in the
   future, and DOB-implied age matches stated AGE within the ±1 year slack
   the generator's own sampling arithmetic allows.
4. Repeats all of the above on both AUGMENTED files, to confirm date
   content survives casing/OCR-noise/mojibake transforms in a form the
   corruption doesn't accidentally turn into a *different but still valid*
   date (which would be a real, worse bug than unparseable garbage).

**Real bug found and fixed by this pass**: French's `fmt_date()` abbreviated
every month with a blanket `MONTHS[d.month-1][:3]` truncation — which
collapses **"juin" (June) and "juillet" (July) to the identical string
"jui"**. A date like "15 jui 1978" is genuinely, unrecoverably ambiguous
between June and July. This had shipped silently through the entire
original French build. Fixed using the verified real French convention
(short months mars/mai/juin/août stay unabbreviated; juillet → "juil";
janvier/février need 4 letters — "janv"/"févr" — to stay distinct from each
other). English's blanket `[:3]` has no equivalent collision (Jan–Dec are
already pairwise-distinct at 3 letters), so no fix was needed there.

The script's own first draft also produced two classes of **false**
positive worth knowing about if you extend it — the same
"validation-methodology false positive" pattern already seen once in
French's build history (§8, item f): a fixed century-pivot heuristic for
2-digit years misread birth years like "60"/"53" as 2060/2053 (100+ bogus
"future DOB" flags); and a naive whole-document regex for "NN years
old"/"NN ans" matched unrelated duration phrases in French prose ("depuis
10 ans" = "for 10 years", not the patient's age), producing 2,307 bogus
mismatches. Both were fixed (context-aware century resolution; anchoring to
the real AGE span instead of a bag-of-words search) before trusting the
results.

**Final result, full corpus, both languages: 0 errors on every check.**
The augmented files show nonzero "unparseable" counts (546 EN / 570 FR) —
this is **expected, not a bug**: every single one is `xf_mojibake` or
`xf_ocr_noise` doing exactly what it's designed to do (visually corrupt
date text so the model learns to still recognize a DATE span despite OCR
garbling). Confirmed by inspection: 100% of the flagged strings contain
either the mojibake artifact character or OCR-style internal word-splitting
("Octo ber", "Ap ril"). The checks that WOULD matter on a corrupted file —
invalid-calendar dates, ordering violations, future DOBs, AGE mismatches —
are all 0 in both augmented files too.

## 8. Bug classes found and fixed (condensed catalog)

Worth knowing before extending either track further — several of these are
*classes* of bug, not one-offs, and could recur in new templates/genres:

- **Literal-placeholder-leak**: format hints like `"DD-MM-YYYY"` baked into
  prose instead of a real placeholder. Caught by a permanent `LEAK_RE`
  filter in `prep_data_{en,fr}.py`.
- **INSZ/RIZIV label mislabeling**: real language-specific administrative
  terms weren't used for the literal display text (§2.2). Now root-fixed
  for English via sampled label fields (§3.4); French uses `id_label_variant`
  augmentation.
- **`{DIAGNOSIS} {DIAGNOSIS}`-style stutters**: two unrelated Case fields
  (a narrative field and a distractor field) coincidentally sampled the
  identical value in one representative recovered document, collapsing
  into what looked like a repeated slot. Caught only by manually reading
  rendered output.
- **Repeated-identical-value in dense tables**: one Case field reused
  verbatim across every cell of a multi-row table (since a Case field's
  value is sampled once per document). Fixed by adding N independently-
  sampled fields (`DX_NUMERIC_2`…`_9`) and wiring one per cell — apply this
  to any new table-shaped genre from the first draft, not after finding the
  bug.
- **Double-title ("Dr dr. X" / "Dr Dr X")**: `NAME_DOCTOR`'s Case value
  already includes a title prefix — writing a literal title before it in
  template prose doubles it. Recurred independently in a second template
  even after being fixed once in a first — check for it explicitly every
  time, don't assume "fixed once" means "can't recur".
- **Literal-prefix-collides-with-own-distractor-pool** (e.g. `"ATCD
  {DX_ABBREV}"` when the `DX_ABBREV` pool itself contains the string
  "ATCD"): silently present in 23-of-50 original French templates for
  multiple sessions before being found. Grep the whole bank for `"<literal
  prefix> {FIELD}"` patterns at the end of any translation/authoring pass.
- **Hardcoded honorific/kinship word before an independently-sampled
  relation field**: e.g. "de heer {NAME_RELATIVE}" glued next to a
  separately-sampled `{RELATIVE_RELATION}` that's ~half the time feminine.
  Fix: drop the honorific before a relative-name slot entirely rather than
  inventing a new field just to patch one contradiction.
- **One-doctor-one-ID rule** (a design rule applied proactively, not a bug
  found): `Case` only stores one `RIZIV` value — if a document names two
  different clinicians, only ONE of them may show the NIHDI/RIZIV field.
- **Validation-methodology false positives**: an imprecise check that
  searches the *whole document text* instead of anchoring to the actual
  span offset will produce false alarms (found twice — once in French's
  original grammar-check history, once in this session's own first draft
  of `validate_dates_deep.py`, §7.5). Anchor every consistency check to a
  real span/slot, never a bag-of-words search.
- **French month-abbreviation collision** (§7.5): "juin"/"juillet" both
  truncating to "jui" under a blanket `[:3]` rule. Now fixed with a real
  per-month abbreviation table.

## 9. Known, honestly-stated limitations

Don't expect these to be silently solved — they're documented, not hidden:

- **Template-skeleton overlap ~65%** in both languages (§7.3) — a real,
  currently-unsolved structural-novelty ceiling.
- **The 6 new genres have only one template skeleton each** (§4) — PII-value
  diversity is excellent within each, wording/structure diversity is not.
- **`anglophone_africa`/`anglophone_asia` are single-country pools**
  (Nigeria/India only) despite the broader "Anglophone Africa/Asia" design
  intent (§3.5) — a real, scoped gap, not yet addressed.
- **No `french_regex.py` or `english_regex.py` inference-layer fork exists
  yet** — the regex/checksum hybrid-scoring layer used at inference time
  hasn't been built for either new track (Dutch's own two regex layers
  aren't even reconciled with each other). This doesn't block training-data
  readiness but will block a real end-to-end eval.
- **No real English-language reference PDF exists** — the 5 real reference
  documents are Dutch-language. English's extraction-noise hard eval
  (`build_hard_extraction_eval_en.py`) reuses the same confirmed failure
  *shapes* (header-table misdetection, mid-word splice) as an explicitly
  stated inferred-from-mechanism assumption, not a real-document-confirmed
  one.
- **3 of the 6 new genres rely on medium-confidence *inferred* layout
  details** (pharmacy, prescription, discharge-meds) — only the sick note
  and radiology report structures are confirmed against a real regulatory
  source, in both languages.
- A dedicated **"genuinely unseen vocabulary" generalization test** now
  exists for both tracks (`ood_stress_test_{en,fr}/build_ood_set_{en,fr}
  _v3_novel_vocab.py`, 6 docs each) — but it's necessarily small (the
  "honest small list" precedent this project applies throughout), and its
  reserved vocabulary must **never** be added to the actual generator pools
  or it stops testing anything.
