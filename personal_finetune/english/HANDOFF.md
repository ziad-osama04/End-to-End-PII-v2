# English-track handoff: replicate the French PII data-generation pipeline

This document is written so you can hand it directly to a fresh Claude Code
session (paste the whole thing as your first message) with no other context
needed. It explains the project, what's already been built for French as the
reference implementation, what's genuinely different about English, and the
exact steps to follow.

---

## 1. Project context (read this first)

This repo (`End-to-End-PII-v2`) has an ongoing PII-detection fine-tuning
track under `personal_finetune/` (+ `TamerBERT/TamerBERT/`). It fine-tunes a
RoBERTa-family model per language to detect PII (names, dates, addresses,
national ID numbers, phone numbers, etc.) in synthetic medical documents,
using entirely synthetic training data generated by a Python script — no
real patient data is ever used.

**Dutch is done and shipped**: `farahelmashad/pii-medroberta-nl-v2`
(indist F1 0.988), built on `CLTL/MedRoBERTa.nl`.

**The project is expanding to 5 more languages**: French, English, Romanian,
Spanish, German. Architecture decision already settled (don't re-litigate
this): **per-language monolingual models**, not a shared multilingual model
and not zero-shot. A published study (arXiv:2412.10918) trained separate
expert models for exactly these 5 languages and got F1 0.95-0.98 across all
of them, beating GPT-4o; general/zero-shot multilingual PII models cap out
around F1 0.6 regardless of architecture family. Only real in-domain
fine-tuning gets to 0.95+.

**Critical fact about this whole project, easy to miss**: French and
English tracks are both **Belgian**, not France-French or UK/US-English.
That means Belgian-national identifier formats (INSZ national-registry
number with its real mod-97 checksum, RIZIV healthcare-provider number,
IBAN "BE" prefix, Belgian phone area codes) are **shared across every
language track** — they don't change with the document language, only the
surrounding prose does. This is the single most important thing to get
right before writing any code.

**Status of each track**:
- Dutch: shipped, done, not being revisited.
- French: base model chosen (`almanach/camembert-bio-base`), and the core
  synthetic-data generator (`personal_finetune/french/pii_table_fr.py`) is
  fully built, researched, and verified. This is your reference
  implementation — read it before writing any English code.
- Spanish: base model chosen (`PlanTL-GOB-ES/bsc-bio-ehr-es`), data
  generation not started.
- English, Romanian, German: **nothing started yet**, including base model
  selection.

## 2. Read the French reference implementation first

Before writing anything, read `personal_finetune/french/pii_table_fr.py` in
full. It's a fork of `TamerBERT/TamerBERT/pii_table.py` (the original Dutch
generator) and its module docstring documents, in detail, exactly what was
kept unchanged (Belgian-structural code) vs. forked (language content) and
why. Treat its *structure and method* as the template to follow for
English — not its content, obviously, since French content doesn't apply.

Also skim `TamerBERT/TamerBERT/pii_table.py` (the Dutch original) and
`personal_finetune/README.md` for the full pipeline this data eventually
feeds into (augmentation rounds, OOD stress-test batteries, Kaggle
training/eval/quantization stages) — you're building the **data generation**
piece; training/quantization is a separate later phase, same as it was
scoped for French.

## 3. English is structurally different from French/Dutch — resolve this before coding

This is the part that doesn't just mechanically copy from French, and it's
important enough that you (or whoever's directing this work) should decide
it explicitly rather than guess.

Flemish (Dutch track) and Walloon (French track) both map cleanly onto a
real Belgian linguistic community with its own region, cities, and native
population. **English does not.** Nobody's ethnic-native-language community
in Belgium is "English" — English speakers in Belgium are functionally
expats, EU/NATO institution staff, international-school families, and
multinational-company employees, heavily concentrated in Brussels
specifically (and, secondarily, wherever multinational employers cluster).
This breaks several assumptions the French/Dutch generator design leans on:

1. **Geography**: should English-track documents be modeled as
   Brussels-concentrated (matching where the real anglophone population
   actually lives), or nationally distributed (since any hospital in
   Belgium could in principle issue an English-language letter for an
   English-speaking patient)? The French generator's population-weighted
   `WALLOON_CITIES` table (real Statbel population weights) doesn't have an
   obvious English analogue — there's no "Anglophone region of Belgium" to
   pull population data for.
2. **Name-origin / demographic stratification**: the Dutch and French
   generators stratify by `name_origin` to model the REAL immigrant-origin
   composition of the *native* population being treated (Flemish or
   Walloon respectively) — this is explicitly a fairness/differential-recall
   measurement tool (see `pii_table_fr.py`'s module docstring and `NAMES`
   comments). For English, the population you're actually modeling is
   fundamentally different: it's an expat/international community, not a
   native-population-with-immigrant-minorities. The realistic origin mix is
   something like UK/Ireland, US, other-EU-staff-using-English-as-lingua-
   franca, and Anglophone-Africa/Asia (Nigeria, India, etc.) — NOT the same
   categories used for French/Dutch. Don't just reuse the French/Dutch
   weight structure; rebuild it around what the English-speaking population
   in Belgium actually looks like.
3. **Street/address naming**: Belgium does not have "English street names."
   A real English-language medical letter about a Brussels patient would
   still show the ACTUAL Belgian street name (French or Dutch — Brussels
   streets are officially bilingual, e.g. "Rue de la Loi / Wetstraat";
   elsewhere it's whichever regional language is official). **Do not invent
   an English-style street-naming convention** — reuse real Belgian street
   names/patterns (borrow from the French or Dutch generator's approach
   depending on where in Belgium the case is set) with English prose around
   them.
4. **Spelling/register convention**: British vs. American English spelling
   (e.g. "oesophagitis" vs. "esophagitis", "anaemia" vs. "anemia") is a real
   decision, not a detail — EU-institution and Belgian-international-school
   English strongly skews British/international convention, not American.
   Recommend British/international spelling as the default, but make this
   an explicit, stated decision, not a fallback default you back into.
5. **Letter register**: should the generated English read like a native
   British/American clinical letter, or like "Belgian clinical
   correspondence written in English by a Belgian doctor" (i.e., Belgian
   phrasing/structure conventions, English vocabulary — which may honestly
   be the MORE realistic register for this specific use case, since the
   underlying institutions and doctors are Belgian)? Decide and document
   this before translating any templates, since it changes how you'll do
   step 5 below.

None of these have an obviously-correct answer baked into the existing
pipeline — surface them to whoever's driving this (your own judgment call,
or ask the team) before you commit code, the same way the French track's
open questions were resolved by asking rather than guessing.

**One place where English is actually *simpler* than French, worth
noting**: French "son"/"sa" (his/her) agree with the GENDER OF THE
POSSESSED NOUN, not the possessor's sex, which broke a naive per-case
`PRONOUN_POSS` slot (see `pii_table_fr.py`'s docstring for the full
explanation) — the field had to be dropped entirely for French. English
"his"/"her" agree with the POSSESSOR's sex, exactly like Dutch's
"zijn"/"haar", so a simple per-case `PRONOUN_POSS` slot works fine for
English. Same recommended fix for the (fully unmarked, in English) patient
noun: English "patient" has no separate masculine/feminine form
(unlike French patient/patiente or Dutch patient/patiente) — there is no
`PATIENT_NOUN_MARKED` distinction to make for English at all.

## 4. Step-by-step method (mirrors what was actually done for French)

1. **Pick the base model first**, the same way French/Spanish were chosen:
   compare real, downloadable English-specific clinical/biomedical
   RoBERTa/BERT-family models (candidates likely include
   `emilyalsentzer/Bio_ClinicalBERT`, `microsoft/BiomedNLP-PubMedBERT`,
   `allenai/biomed_roberta_base`, plain `roberta-base` as a baseline) on
   architecture, pretraining recipe, and independently-benchmarked clinical
   NER accuracy — same rigor as the French/Spanish briefs. Flag explicitly
   that most English clinical-BERT models are pretrained on American
   hospital text (e.g. MIMIC-III ICU notes) — note this as a domain-match
   caveat given the Belgian/international target population and the
   British-leaning spelling decision from section 3.

2. **Research the real facts before writing any content pools**, the same
   way French did (don't skip this — it's what caught real errors last
   time): whatever geography scope you settle on (Brussels-concentrated vs.
   national), the realistic expat-origin demographic mix, and which real
   Belgian hospitals actually serve significant international/English-
   speaking patient populations (Brussels university hospitals and
   EU-quarter-adjacent clinics are a reasonable starting point — reuse the
   real hospital data already gathered for French/Dutch where the same
   institutions apply, e.g. `CHU Saint-Pierre`, `Cliniques universitaires
   Saint-Luc`, `CHU Brugmann` are already in
   `personal_finetune/french/pii_table_fr.py`'s `HOSPITAL_STANDALONE` list).

3. **Fork `pii_table.py` into `personal_finetune/english/pii_table_en.py`**,
   following `pii_table_fr.py`'s exact split: keep unchanged everything
   Belgian-structural (`make_insz`, `make_riziv`, `make_iban_be`,
   `luhn_card`, `fmt_insz`, `fmt_riziv`, `fmt_iban`, `make_phone`,
   `AGE_BANDS`, `NOISE_OPS`, the label-scheme dicts, `render()`, `audit()`),
   fork everything else with real English-language content resolved per
   section 3's decisions above.

4. **Recover the real Dutch templates from `train.jsonl` and translate
   them** — do NOT hand-author templates from scratch. This was the single
   biggest time-saver on the French track: `TamerBERT/TamerBERT/train.jsonl`
   (54MB, 6,417 rendered documents) still has the original templates
   embedded in it. Each record's `spans` carry a `slot` field and each
   record's `meta` carries a `template_hash` (69 unique values, ~93 docs
   each). Recover the masked templates by, for one representative record
   per `template_hash`, replacing each span's `text[start:end]` with
   `{slot}` (sorted by `start` descending so earlier replacements don't
   shift later offsets). Reuse `prep_tamerbert_data.py`'s
   `LEAK_RE = r"DD-MM-YYYY|MM/YYYY"` filter to drop the ~19 known-bad
   templates (literal format-hint text baked into the prose instead of a
   real placeholder) — what's left should land near the ~50 templates the
   README documents as the real original count, which is a good
   self-consistency check that the recovery worked.
   Translate the ~50 recovered templates into English per the register
   decision from section 3. **Translation quality matters enormously here
   — verify it, don't just translate once and move on.** What worked for
   French: produce a translation, then run a SEPARATE adversarial review
   pass (a second Claude agent, or a fresh conversation) whose only job is
   to find translation problems (mistranslated/inaccurate medical
   terminology, unnatural phrasing or source-language-calque artifacts,
   wrong register, any `{slot}` placeholder damaged or dropped) before
   treating the translation as final.

5. **Fork the augmentation pipeline**
   (`personal_finetune/augmentation/augment_v4.py` →
   `augment_en.py`): keep the transform mechanics unchanged (`xf_casing`,
   `xf_ocr_noise`, `xf_mojibake`, `xf_diacritic_honorific`,
   `xf_inline_mention`, `xf_org_context`, `xf_email_header`,
   `gen_non_medical`), replace the verbatim pools (companies, products,
   non-medical letter templates, honorifics, email domains/locals,
   signoffs, department names) with real Belgian-English-appropriate
   content per section 3's decisions.

6. **Build a fresh English OOD stress-test battery**
   (`ood_stress_test_en/build_ood_set_en.py`), covering the same category
   types the Dutch/French batteries found valuable (document-type
   diversity, casing variation, non-medical no-PII probe, hard-negative
   ID-shape probes, sliding-window boundary-crossing doc, organization/
   address hard negatives) — authored fresh, not translated from the
   French/Dutch batteries, since the hard-negative classes (homographs,
   abbreviations) need to be genuinely English ones, not translated ones.

7. **Run the audit.** `pii_table_fr.py`'s `audit()` function is
   language-agnostic (statistical checks only) — reuse it as-is against
   whatever `Case` dataframe the English generator produces, and actually
   run it (`python pii_table_en.py -n 2000 --out ... --audit`) before
   calling this phase done. Also run `--demo` and read the actual rendered
   output yourself — don't assume the code is correct without looking at
   what it actually generates.

## 5. Concrete lessons learned building the French track (avoid repeating these)

- **Verify grammatical-agreement assumptions per language before reusing a
  field design from another language.** The `PRONOUN_POSS` field worked
  fine for Dutch, silently broke for French (see section 3), and is fine
  again for English. Don't assume a design choice transfers just because it
  worked for the previous language.
- **Ground every demographic/geography/vocabulary claim in real, verified
  research** (population figures, official hospital registries, medically
  verified clinical terminology) rather than plausible-sounding invented
  content. Use web research explicitly for this; don't rely on background
  knowledge alone for anything that will become training-data content.
- **When asked for comprehensive real-world coverage (e.g. "as many real
  hospitals as you can find"), actually be comprehensive** — a first pass
  at the French hospital list under-delivered (35 institutions when ~80+
  real ones were readily available from the same research); lean toward
  including everything real you found rather than curating down to a
  "reasonable-looking" subset.
- **Watch character encoding on any content with special characters.** The
  first full draft of the French generator had accidentally stripped every
  French accent (é, è, à, ç, œ) — authentic French text needs them; verify
  actual file bytes are correct UTF-8 by writing output to a file and
  reading it back, not just by eyeballing a terminal (terminal rendering
  can itself be misleading independent of whether the underlying file is
  correct).
- **Actually run the code and read the output** at every checkpoint — a
  template phrasing bug (an English-inappropriate construction analogous to
  French's "Le/la {patient}" slash-placeholder artifact) was only caught by
  running `--demo` and reading the rendered text, not by reading the source
  code alone.
- **Don't force a weak match to hit a target count.** The French
  municipality-homograph hard-negative list intentionally shipped with only
  4 entries instead of matching Dutch's 9, because most Walloon place names
  genuinely have no real French-word collision — an honest, smaller,
  expandable list beats force-fitting near-misses. The same principle will
  likely apply to whatever the English equivalent hard-negative categories
  turn out to be.
