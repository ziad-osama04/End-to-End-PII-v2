# Dutch PII model: full fine-tuning history, trial by trial

**Purpose of this document.** A complete, evidence-grounded account of every
trial run that led to the shipped Dutch model (`farahelmashad/pii-medroberta-nl-v2`),
what changed between runs, and — the part usually lost once a project ships —
*how each claim was actually validated*, not just what the final numbers were.
Every number below was pulled directly from the real `eval_report.json` files
still sitting in each trial's `outputs/*/reports/` directory, or from the
final `pii_model_results.pdf`, not reconstructed from memory.

This document is Dutch-only. For the French build's full chronology (every
bug found, every validation pass, the new document genres) and the open
questions/method for English, see
**`personal_finetune/english/HANDOFF.md`** — that document's Part 1 is a
condensed "lessons learned" version of everything below; this document is
the full trial-by-trial account those lessons were distilled from.

---

## 1. Base model and task framing

- **Base model**: `CLTL/MedRoBERTa.nl` — RoBERTa-base architecture, pretrained
  from scratch on real Dutch hospital notes (not continual-pretrained from a
  general-purpose model, and not literature-only). ~100M parameters.
- **Task**: token classification (BIO tagging) via
  `AutoModelForTokenClassification`, sliding-window tokenization
  (`MAX_LEN=512`, `STRIDE=128`), overlap resolved by keep-longest span
  reconciliation.
- **Training data**: entirely synthetic, generated by
  `TamerBERT/TamerBERT/pii_table.py` — real Belgian reference data (city/
  zipcode tables, name pools stratified by origin, real mod-97 INSZ/RIZIV
  checksums, real Belgian phone-number-format tables) sampled via
  `random`/`Faker`. No LLM anywhere in per-document generation, and no real
  patient data anywhere in the pipeline.
- **Hybrid detection design**: some entity types are detected by the
  fine-tuned model, others by a deterministic regex/checksum layer that sits
  outside the model entirely. This split was **not** assumed — it was
  decided by ablation (§4).

## 2. How validation actually worked — read this before the trial log

Every trial below reports (a subset of) four distinct eval surfaces, each
proving something different. Confusing them is the single easiest way to
believe a model generalizes when it doesn't:

| Surface | What it actually tests |
|---|---|
| **`indist`** | Unseen *documents*, but from template structures the model saw during training. High indist F1 proves the model learned the field-value patterns (name shapes, date formats, checksum-adjacent context) well. It proves **nothing** about unseen document structure. |
| **`eval_heldout_templates`** | Documents rendered from template structures held out of training entirely (split by `template_hash`, not by document — see §2.1). This is the real generalization test for structural novelty within the same synthetic-generation family. |
| **`real`** | The 5 real reference documents (`org_data_filled_labeled.jsonl`, the "HealthOne Nova" / `AZORG` letters). Small (n=5), but the only ground truth not generated by the same pipeline being evaluated. |
| **`ood`** (and `ood_v2`–`v6`) | Hand-authored or systematically-perturbed documents built specifically to probe a known or suspected weakness (casing, homographs, partial redaction, sliding-window boundaries, etc.) — eval-only, never trained on. |

**A result that looks good only on `indist` is not evidence of anything
beyond "the generator's own patterns were learned."** The project's central,
hard-won lesson (§5) is that early rounds looked excellent on `indist`
(0.986+) while failing badly under real structural novelty — that gap is
exactly what the later rounds spent most of their effort closing.

### 2.1 Why the split is template-hash-based, not document-based

`prep_tamerbert_data.py` groups all rendered documents by `template_hash`
first, **then** splits: 20% of *templates* (not documents) are held out
entirely into `eval_heldout_templates.jsonl`, and only the remaining 80%
of templates contribute documents to the train/`eval_indist` split (90/10
within that pool). A plain random document-level split would let the model
see 90% of instances of every template structure and creates a false sense
of generalization — the held-out set would still contain familiar
skeletons with just different field values swapped in. Splitting by
template hash is what makes `eval_heldout_templates` a real test of
structural novelty rather than a second flavor of `indist`.

A `LEAK_RE` filter (`r"DD-MM-YYYY|MM/YYYY"`) also runs at this stage,
dropping any template where a literal placeholder-hint string leaked into
the template prose instead of being replaced by a real field — a bug found
in ~19 of the original ~69 templates (§5, item 1).

## 3. Trial-by-trial log

Numbers below are `model_only_strict` unless stated otherwise — full
pipeline (model + regex + checksum layer). Directory names are the actual
Kaggle-kernel output folders in `personal_finetune/`; exact chronological
order between `kaggle_stage1_trial` and the early `kaggle_tamerbert_trial`
runs is inferred from naming and label-scheme evolution, not from a
timestamped log — flagged where uncertain.

### `kaggle_stage1_trial/trial3` — early exploration, split-address label scheme
Label scheme: NAME, DATE, ORGANIZATION, **STREET, BUILDING_NUMBER, ZIP_CODE,
CITY** (address split into 4 separate labels), PHONE, AGE.
- **Overall F1 0.9940** (precision 0.9918, recall 0.9962, tp 6564/fp 54/fn 25).
- Every label ≥0.987, several at 1.000 (STREET, CITY).
- This is an early, single-trial checkpoint under the split-address scheme,
  before the address-merge decision (§4.1) was made.

### `kaggle_generalization_trial/gen1` — a real, severe generalization failure
Same split-address label scheme as `trial3`, evaluated on a structurally
different distribution.
- **Overall F1 collapsed to 0.4346** (precision 0.5715, recall 0.3507).
- Catastrophic per-label breakdown: STREET F1 **0.000**, PHONE F1
  **0.0012**, CITY F1 0.059, BUILDING_NUMBER F1 0.063, DATE F1 0.370.
  AGE held up best (F1 0.742) but even that was well below the ~0.99 seen
  on `trial3`.
- This is the concrete, numeric evidence behind the project's core lesson:
  a model can look essentially perfect on one distribution (`trial3`,
  F1 0.994) and fail almost completely on a distribution built differently,
  even within the same synthetic-generation family. This result is the
  most likely origin of the later, disciplined multi-surface eval
  methodology in §2 — treat it as the reason that methodology exists, not
  as an isolated bad run to explain away.

### `kaggle_tamerbert_trial/run2` → `run9` — the main development line
This is the lineage that became the shipped model (the final run's own
`Trial ID` field literally reads `tamerbert-final-v1`). Label scheme
switched to **merged single ADDRESS** (§4.1) starting here. Every run in
this line reports `indist` alongside `regex_only_strict` (the checksum/regex
layer scored in isolation, for comparison against the model).

| Run | indist F1 | DATE F1 (model) | Notes |
|---|---|---|---|
| run2 | 0.9859 | 0.9487 | baseline of the merged-ADDRESS line |
| run3 | 0.9862 | 0.9485 | |
| run4 | 0.9863 | 0.9482 | |
| run5_seed123 | 0.9859 | 0.9481 | **seed-stability check** — differs from run4 by 0.0004 F1, confirming the result isn't a seed-lucky fluke |
| run6_final | 0.9861 | 0.9479 | |
| run7_final_regexfix | 0.9857 | 0.9482 | regex-layer fix applied (see §5, item 2) — model-side numbers essentially unchanged, as expected, since the fix was in the regex layer not the model |
| run8_augmented | 0.9866 | 0.9489 | first augmentation round applied — indist ADDRESS reaches 1.000 |
| run9_augmented_v2 | 0.9862 | 0.9491 | second augmentation round |

Across every run in this line, `regex_only_strict` overall sits at
**0.9211–0.9215** — meaningfully below the model's ~0.986. The regex
layer's own DATE F1 is **0.867–0.868**, well below the model's ~0.948 on
the same label. This comparison is the actual evidence behind the
`merge_drop_all` decision (§4.2): the model doesn't just match the regex
layer on DATE/AGE/PHONE, it clearly beats it, so letting the model own
those labels outright and discarding regex entirely for them is a measured
decision, not a guess.

Also visible directly in the data: **DATE is consistently the weakest
model-trained label** across every single run (0.948–0.949, versus
0.99–1.00 for every other label) — this is stable enough across 8 runs
and 2 seeds that it's a real, structural property of the label (dates have
far more surface-format variety than names/phones/addresses — see
`pii_table.py`'s `fmt_date()`, which samples from ~14 distinct formats),
not noise.

### `kaggle_tamerbert_trial_addrsplit/run1` — re-testing the address-split question
Split-address scheme (STREET/ZIPCODE/CITY separate), run against the
by-then more mature pipeline, to check whether the earlier ADDRESS-merge
decision should be revisited.
- **indist overall F1 0.9888** — numerically *higher* than the merged
  scheme's ~0.986 at this point.
- **This is the important methodological trap this ablation exists to
  demonstrate**: judged on `indist` alone, splitting the label looks like
  a clear win. The decision to keep ADDRESS merged was made on the **real
  document surface**, not indist — splitting measurably hurt real-document
  precision (1.000 → 0.968) with no compensating gain on OOD. This file
  doesn't carry the real-surface numbers itself (only `indist` and a
  `model_only_addrmerg...` key are visible in this report), so treat the
  indist number here as context, not as the deciding evidence — the
  deciding evidence lives on the `real` surface and should be pulled from
  that run's full report before citing an exact real-surface number in a
  future write-up.

### `kaggle_discovery_eval/run1` and `run2` — cheap, inference-only bug-hunting
Numbers are **identical** to `run7_final_regexfix` (0.9857) and
`run8_augmented` (0.9866) respectively — confirming these were not new
training runs at all, but inference-only reuse of an already-trained
checkpoint (via `SKIP_TRAINING=1` + `kernel_sources` mounting the earlier
kernel's saved model), used to test new OOD stress batteries against an
existing model with zero GPU retraining cost. This is a deliberate,
reusable pattern: **before retraining, check whether the question can be
answered by re-evaluating an existing checkpoint against new eval data.**

### Rounds not represented by a surviving `eval_report.json`, confirmed via the final results report
Two further rounds happened after `run9`, both already known from the
shipped model's own results (`pii_model_results.pdf` — see §7) and the
project's ongoing record, though their intermediate per-run JSON reports
weren't located in this pass:
- **`tamerbert-org-boundary-v1`** — a round specifically addressing
  organization-name boundary extraction (making sure the org name is
  correctly and fully extracted from surrounding context, not truncated or
  over-extended).
- **`tamerbert-final-v1`** (the shipped model) — trained under an explicit
  deadline, on **6,469 documents** (3,348 original + 3,121 augmented,
  `train_augmented_v5.jsonl`), described in the checkpoint-curve log built
  into the final results report as:
  ```
  step 250: 0.9776   step 1500: 0.9861
  step 750: 0.9843   step 2250: 0.9866
  step 1250: 0.9854  step 2750: 0.9865 (final)
  ```
  Plateaus by step ~1500 with no degradation through 2750 — the explicit
  check that ruled out overfitting before shipping.

## 4. Key decisions, and the evidence behind each

### 4.1 Single merged `ADDRESS` label, not split into STREET/ZIPCODE/CITY
Decided by ablation, not preference. `kaggle_tamerbert_trial_addrsplit/run1`
showed splitting actually looks *better* on `indist` (0.9888 vs ~0.986) —
the decision to keep it merged was made because splitting cost real-document
precision (1.000 → 0.968) with no compensating OOD gain. **Lesson embedded
in this decision**: judge label-scheme changes on the real/OOD surfaces,
never on indist alone (§2, §3's addrsplit entry).

### 4.2 `merge_drop_all` — regex excluded entirely for AGE/DATE/PHONE
The model outright beats the regex-only layer on every run for DATE
(model ~0.948 vs regex ~0.867) — see the `run2`–`run9` table in §3. Given
that gap, letting the model own AGE/DATE/PHONE completely (dropping regex
predictions for these three rather than merging/falling back to them) beat
the `fallback` merge strategy on every eval surface tested.

### 4.3 Institutional/hospital names ARE correctly labeled NAME
An earlier pass flagged this as apparent model confusion ("institutional-
name ambiguity") and nearly built a fix for it. Checking all 5 real
ground-truth documents showed the hospital name is genuinely labeled NAME
throughout the real data too (`ORGANIZATION → NAME` in the `FLAT9` label
scheme is intentional, per `pii_table.py`'s own docstring) — the one
document that looked inconsistent had a bad gold label, not a bad
prediction. **Lesson: verify against ground truth before "fixing" what
looks like model confusion** — this exact mistake pattern recurred later
in the French track for an unrelated reason (see HANDOFF.md §2.5f).

### 4.4 Casing-lock-in fix
ALL-CAPS documents collapsed the model to F1=0.613, Title-Case-Every-Word
to F1=0.778 (vs ~0.98 baseline) — confirmed as a genuine model weakness
specifically (regex-only F1 stayed ~0.90–0.93 under the same transforms,
since digit-pattern regexes are case-insensitive by construction). Fixed
by adding a casing-transform augmentation round (part of the `run8`/`run9`
augmentation jump visible in §3's table), and confirmed closed on a
genuinely fresh third-round OOD battery that was never used to design the
fix.

## 5. Bugs found, in the order they were found

1. **19 of ~69 templates had a literal-placeholder-leak bug** — text like
   `"DD-MM-YYYY"` baked into template prose instead of a real placeholder.
   Caught by `LEAK_RE`, now a permanent filter in `prep_tamerbert_data.py`.
2. **Three regex/checksum-layer bugs**: (a) AGE false-positive on
   "above/below N years" reference-range disclaimer text; (b) a missing
   `YYYY/MM/DD` slash-separated date format; (c) INSZ/RIZIV regex failing
   whenever a sentence-final period immediately followed the number — fixed
   by narrowing the trailing lookahead from `(?![\d.\-/])` to `(?!\d)`.
   Confirmed via real-document testing (regex-only F1 on real docs rose to
   0.988 after fix c specifically) — **not yet ported back to the original
   `patterns.py` source**, check before assuming it's fixed there.
3. **Casing lock-in** — §4.4.
4. **Sliding-window boundary crossing tested and confirmed NOT a real
   problem** — a span deliberately engineered to straddle a stride-window
   boundary was still fully recovered via `resolve_overlaps`.
5. **The real root cause of the OOD ceiling was narrow structural template
   diversity, not field-format diversity.** Field-format variety (phone
   formats, date formats, name variety) was already excellent even in
   `run2`. What was missing was structural/genre diversity — the training
   set was ~40–50 near-identical clinical-letter-shaped templates. This is
   the single biggest lesson of the whole project, and the direct reason
   the French track later built 6 additional non-letter document genres
   rather than just more letters.
6. **Two non-identical regex/pattern layers exist and were never
   reconciled**: `backend/src/detection/dutch_regex.py` (the team's shared
   code) vs. this track's own inlined regex in `train_and_eval.py`. A fix
   made in one is not guaranteed present in the other. Open, known debt —
   flag it to whoever owns the shared `backend/src/detection/` code rather
   than silently fixing it inside `personal_finetune/`.

## 6. OOD stress-test buildout (eval-only, never trained on)

Six rounds, `ood_stress_test_v1` through `v6` (~45 hand-authored categories
total — read the actual directories directly for the full category list,
this is a summary): name diacritics, adversarial casing, partial redaction,
non-medical false-positive probes, numeric hard-negative ID types,
sliding-window boundary crossing, homoglyph substitution, and more. OOD
strict F1 trajectory across the project: **0.66 → 0.72–0.87 (round-1
fixes) → 0.803 (final, shipped)**. OOD is a documented, accepted weak
point of the shipped model, not something still being actively chased —
the gap between ~0.99 indist and 0.80 OOD is real and known, not hidden.

## 7. Final model and quantization

Real numbers, pulled directly from `pii_model_results.pdf`:

| Surface | Docs | Support | Precision | Recall | F1 |
|---|---|---|---|---|---|
| indist | 372 | 13,245 | 0.987 | 0.988 | **0.988** |
| ood | 14 | 73 | 0.750 | 0.863 | **0.803** |

Per-label indist F1: NAME 0.999, ADDRESS 1.000, ORGANIZATION 0.999, AGE
0.996, INSZ/RIZIV/URL 1.000, **DATE 0.949** (the one consistently weaker
label, same pattern seen across every `run2`–`run9` trial in §3).

**Quantization** (dynamic INT8, `onnxruntime.quantization.quantize_dynamic`,
no calibration dataset needed): 501.8MB → 126.2MB (**-74.9%** size),
mean latency 991ms → 667ms (**1.48×** faster), indist F1 0.988 → 0.987
(quantization cost was negligible). Both fp32 and INT8 models are public:
`huggingface.co/farahelmashad/pii-medroberta-nl-v2` and
`...-int8-onnx`.

## 8. Validation principles to carry into any new language

Distilled from everything above — this is the actual "how we validated
each time" answer:

1. **Never trust `indist` alone.** It only proves the generator's own
   patterns were learned (§2, §3's `addrsplit` and `generalization_trial`
   entries are the two clearest numeric demonstrations of this in the
   whole project).
2. **Split holdout by template structure, not by document** (§2.1) — a
   document-level split cannot detect memorization of template skeletons.
3. **Before retraining to answer a new question, check whether an existing
   checkpoint can answer it via inference-only re-evaluation** (§3's
   `discovery_eval` entries) — cheap, and was the actual working method
   used repeatedly in this project, not a one-off shortcut.
4. **Check seed-stability at least once** (`run4` vs `run5_seed123`,
   §3) before trusting that a result is a real effect rather than
   noise.
5. **When a label-scheme or architecture ablation shows conflicting signals
   across surfaces (§4.1's address-split case: better on indist, worse on
   real), the real/OOD surface wins the decision, not indist.**
6. **Verify against real ground truth before "fixing" something that looks
   like model confusion** (§4.3) — the fix might be wrong, not the model.
7. **Manually read a sample of rendered documents, not just automated span
   checks** — several real bugs in this project's history (and, per
   HANDOFF.md, several more in French) were only caught this way.
8. **A confirmed root cause matters more than a plausible one** — the OOD
   ceiling was diagnosed as narrow structural diversity (§5, item 5) only
   after ruling out field-format diversity directly, not assumed from
   first principles.
